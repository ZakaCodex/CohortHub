# منظومة الدفعة الجامعية المتكاملة (Telegram Bot + Mini App) — التوثيق التقني الشامل

منظومة أكاديمية متكاملة ومفتوحة المصدر لإدارة الدفعات الجامعية عبر **بوت تيليجرام (Telegram Bot)** و**تطبيق مصغّر (Telegram Mini App)** مرتبطَين لحظيًا بقاعدة بيانات **Supabase (PostgreSQL)** وواجهة برمجية **FastAPI** على **Vercel**.

صُمّم المشروع ليعمل بنسخة مستقلة لكل دفعة في أي تخصص أو مستوى جامعي، مع إمكانية التخصيص الكامل للهوية والمجموعات عبر إعداد واحد (`COHORT_CONFIG_JSON` أو `cohort.json`) ودعم التحديث السلس عبر **GitHub Fork (Sync fork Upstream)** دون تعارضات.

---

## 1. المعمارية التقنية وهيكل المستودع

تتكوّن المنظومة من أربع طبقات مترابطة تعمل معًا بتكامل لحظي:

| المجلد / الملف | الطبقة التقنية | بيئة الاستضافة | الوظيفة الأساسية |
| :--- | :--- | :--- | :--- |
| `core/` | المكتبة المشتركة (Python) | مشتركة (Vercel + Bot) | منطق التحقق، توقيت صنعاء، مصادقة `initData`، الصلاحيات، توليد الباركود `Code 128`، بناء ملفات Excel، المساعد الذكي، وهوية الدفعة `cohort.py` |
| `api/` | الخادم البرمجي (FastAPI) | Vercel Serverless | نقاط النهاية `/api/*` لتشغيل الـ Mini App، مع دعم `ETag / 304 Not Modified` لتقليل استهلاك الشبكة |
| `public/` | واجهة التطبيق المصغّر (SPA) | Vercel CDN | واجهة عربية سريعة (`HTML/CSS/Vanilla JS`) مع تخزين محلي ذكي (`SWR` + `Service Worker`) ومعاينة حية `#demo=...` |
| `bot/` | بوت تيليجرام (`python-telegram-bot`) | Orihost / VPS | استقبال وإرسال الملفات الفعلية (`file_id` / `copyMessage`)، جلسات تسليم الواجبات ومشاركات «شارك»، أوامر `/where` و`/backup`، وعامل الخلفية `worker.py` |
| `supabase/` | قاعدة البيانات (PostgreSQL) | Supabase Cloud | ملفات الترحيل `0001` إلى `0015` (جداول محمية بـ RLS، ودوال `RPC` ذرّية بصلاحية `service_role` فقط) |
| `scripts/` | أدوات التشغيل والصيانة | سطر الأوامر (CLI) | توليد مجموعات الدفعة `setup_cohort.py`، استيراد الطلاب `import_students.py`، استرجاع النسخة الاحتياطية `restore_backup.py`، وتحديث البصمة `bump_assets.py` |
| `tests/` | الاختبارات الآلية (`unittest`) | محلي / CI | `175` اختبارًا تغطي كافة تدفقات البوت والواجهة والقاعدة بنسخ محاكاة معزولة (Stubs) |

## 2. مصفوفة الأدوار والصلاحيات (RBAC)

تُدار الصلاحيات مركزيًا من جدول `role_permissions` وجدول المنح `role_grants` في قاعدة البيانات، ويقتصر دور الواجهة على إظهار أو إخفاء الأزرار بينما يتم التحقق الفعلي داخل دوال PostgreSQL (`require_perm` / `has_perm`):

| الدور البرمجي | المسمّى في النظام | النطاق (`Scope`) | الصلاحيات والميزات المتاحة |
| :--- | :--- | :--- | :--- |
| `guest` | زائر | عام (`any` / `own`) | تصفح وتحميل الملفات الدراسية، خوض اختبارات MCQ، واستخدام المساعد الذكي (`5` رسائل يوميًا للذكاء الاصطناعي؛ والأسئلة المبرمجة مجانية بلا حد) |
| `student` | طالب الدفعة | شخصي (`own`) | كل ميزات الزائر + تسليم الواجبات وتعديلها واسترجاعها، استعراض سجل الحضور النظري، استخراج باركود البطاقة الجامعية (`3` مرات يوميًا)، تقديم وتعديل التظلمات، المشاركة والتصويت في «شارك»، ورفعه لـ `10` رسائل يومية في المساعد الذكي |
| `deputy` | نائب مندوب | المجموعة النظرية (`group`) | كل ميزات الطالب + مسح باركود الحضور وإدارة أجهزة المسح، وفتح جلسة حضور نظري بالنيابة عند تفعيل خيار «غياب المندوب» (`delegate_absent`) |
| `committee` | عضو لجنة علمية | المجموعة / عام | كل ميزات الطالب + رفع الملفات الدراسية للمجتمع (`files.upload`) وحذف ملفاته الخاصة (`own`)، رفع اختبارات MCQ من Excel (`mcq.upload`)، إنشاء وإدارة الواجبات لمجموعته، كتابة التقارير اليومية والأسبوعية لمجموعته، نشر حملات «شارك» وإشعارات مجموعته، والمسح/فتح الحضور عند غياب المندوب |
| `delegate` | مندوب مجموعة | المجموعة النظرية (`group`) | كل ميزات الطالب + فتح وإغلاق جلسات الحضور النظري مباشرة، إدارة أجهزة المسح وتصحيح سجلات الحضور مع السبب وتصدير Excel، فتح وإغلاق دورات التظلمات لمجموعته وتصدير الكشف المجمّع، إنشاء وإدارة الواجبات، نشر حملات «شارك»، وإرسال إشعارات يدوية تتجاوز الكتم لمجموعته |
| `doctor` | دكتور / معيد | مقرراته (`own`) | واجهة مخصصة لعرض واجبات المجموعات المسندة إليه فقط، الضغط على زر «✔️ تم الاستلام» في مجتمع التسليمات، وتصدير كشف Excel (`1` سلّم / `0` لم يسلّم) لكل واجب أو لجميع واجبات المجموعة |
| `developer` | مطوّر النظام | شامل (`any`) | صلاحية كاملة على جميع المجموعات والميزات + لوحة المطوّر الشاملة (إدارة الطلاب واستيراد Excel وفك الارتباط، حظر الزوار، منح وسحب الأدوار، إدارة المواد والدكاترة وربط التدريس، ربط المجتمعات والـ Topics عبر `/where`، سلة المحذوفات، سجل النشاط، مراقبة `outbox`، والنسخ الاحتياطي `/backup`) |

## 3. تخصيص المشروع لأي دفعة وتخصص (ودعم Sync Fork بلا تعارض)

يدعم المشروع تشغيل نسخة مستقلة لكل دفعة (حتى `12` مجموعة نظرية و`60` مجموعة عملية، مع قبول تفاوت عدد المجموعات العملية لكل مجموعة نظرية).

### الطريقة الأولى (الموصى بها): عمل Fork بدون تعديل أي ملف في المستودع (Zero-Conflict Fork)

لتتمكن أي دفعة من عمل **Fork** للمستودع على GitHub واستقبال تحديثاتك المستقبلية بضغطة زر عبر **Sync fork ← Update branch** دون حدوث أي تعارض في الملفات (`Merge Conflict`):

1. **اعمل Fork للمستودع** على GitHub واترك ملفَي `cohort.json` و`supabase/seed_groups.sql` دون أي تعديل.
2. **اضبط هوية الدفعة عبر متغير البيئة `COHORT_CONFIG_JSON`** (يقرأه `core/cohort.py` بأولوية أعلى من ملف `cohort.json`):
   ضع JSON إعدادات الدفعة كسطر واحد في **Vercel (Environment Variables)** وفي ملف **`.env`** على خادم البوت (Orihost):
   ```env
   COHORT_CONFIG_JSON={"specialization":"هندسة البرمجيات","batch":"27","level":"المستوى الأول","theory_prefix":"SE1_G","practical_per_theory":[2,3,2,3]}
   ```
   - `specialization`: اسم التخصص (يظهر في ترويسة التطبيق ورسائل البوت ودليل المساعد الذكي).
   - `batch`: رقم أو رمز الدفعة.
   - `level`: المستوى الدراسي (اختياري، يظهر في شاشة الترحيب).
   - `theory_prefix`: بادئة المجموعات النظرية (أحرف إنجليزية كبيرة وأرقام و`_`؛ المثال أعلاه ينتج `SE1_G1` إلى `SE1_G4`).
   - `practical_per_theory`: مصفوفة تحدد عدد المجموعات العملية التابعة لكل مجموعة نظرية بالترتيب (المثال `[2,3,2,3]` ينتج `10` مجموعات عملية مرقمة تسلسليًا: `G1–G2` للأولى، `G3–G5` للثانية، `G6–G7` للثالثة، `G8–G10` للرابعة).
3. **ولّد كود SQL للمجموعات على الشاشة مباشرة (`--stdout`)** دون تعديل ملفات Git:
   ```bash
   COHORT_CONFIG_JSON='{"specialization":"هندسة البرمجيات","batch":"27","level":"المستوى الأول","theory_prefix":"SE1_G","practical_per_theory":[2,3,2,3]}' python3 scripts/setup_cohort.py --stdout
   ```
   انسخ الناتج وشغّله في **Supabase SQL Editor** بعد تشغيل ملفات الترحيل.
4. **مزامنة التحديثات المستقبلية (`Sync fork Upstream`)**:
   - عند رفع تحديث جديد في المستودع الأصلي، يضغط مشرف الدفعة على **Sync fork ← Update branch** في GitHub؛ فيندمج الكود بنظافة تامة (`Fast-Forward`) ويعيد Vercel نشر الواجهة والـ API تلقائيًا.
   - على خادم البوت (Orihost)، يشغّل المشرف `./scripts/update_bot.sh` (أو `git pull --ff-only`) ويعيد تشغيل البوت.
   - إذا تضمّن التحديث ملف ترحيل جديد في `supabase/migrations/`، يُشغَّل الملف الجديد في Supabase SQL Editor.

### الطريقة الثانية: التعديل المباشر لملف `cohort.json` (لنسخة مستقلة لا تستخدم Sync Fork)
1. عدّل ملف `cohort.json` في جذر المشروع (انظر المثال في `cohort.example.json`).
2. شغّل `python3 scripts/setup_cohort.py` ليحدّث الملف `supabase/seed_groups.sql`، ثم شغّل محتواه في Supabase SQL Editor.

## 4. الإعداد والتشغيل الكامل خطوة بخطوة

### الخطوة 1: إنشاء البوت في BotFather
1. افتح `@BotFather` في تيليجرام وأنشئ بوتًا جديدًا بالأمر `/newbot` واحتفظ بـ **`BOT_TOKEN`** ومعرّف البوت **`BOT_USERNAME`**.
2. أضف البوت مشرفًا (`Administrator`) في مجموعات/مجتمعات الدفعة ومجتمعات الدكاترة، وفعّل له صلاحيات: **إرسال الرسائل، تعديل الرسائل، حذف الرسائل، وإدارة المواضيع (Manage Topics)**.

### الخطوة 2: إعداد قاعدة البيانات في Supabase
1. أنشئ مشروعًا جديدًا في Supabase، ومن **Project Settings ← API** انسخ:
   - `Project URL` ← يُوضع في `SUPABASE_URL`.
   - `service_role secret` ← يُوضع في `SUPABASE_SERVICE_KEY` (مهم: استخدم مفتاح `service_role` وليس `anon` لأن جميع الجداول محمية بـ RLS مغلق).
2. افتح **SQL Editor** في Supabase، وشغّل ملفات الترحيل التالية بالترتيب (جميعها آمنة لإعادة التشغيل `idempotent`):
   1. `supabase/migrations/0001_core.sql` — الجداول الأساسية، المجموعات، الأدوار والصلاحيات، الربط الأكاديمي، و`app_bootstrap`.
   2. `supabase/migrations/0002_files_assignments.sql` — الملفات، المسودات، الواجبات، التسليمات، وطابور الإشعارات `outbox`.
   3. `supabase/migrations/0003_attendance_affairs_support.sql` — الحضور النظري، أجهزة المسح، الباركود، التظلمات، المساعد الذكي، وتذاكر الدعم.
   4. `supabase/migrations/0004_reports_sharek_mcq_dev_doctor.sql` — التقارير اليومية والأسبوعية، شارك، اختبارات MCQ، شاشة الدكتور، ولوحة المطوّر.
   5. `supabase/migrations/0005_reliability.sql` — قفل التسليمات، الحجز الزمني `90` ثانية، التراجع التصاعدي، وإنهاء الرفع غير المكتمل.
   6. `supabase/migrations/0006_ai_savings.sql` — الكاش الدائم للذكاء الاصطناعي `ai_cache` وعدم خصم الحصة على الأسئلة الجاهزة.
   7. `supabase/migrations/0007_assistant_limits.sql` — ضبط الحصة اليومية (`10` للطالب و`5` للزائر).
   8. `supabase/migrations/0008_search_files_limit.sql` — رفع سقف مرشّحي بحث الملفات إلى `400`.
   9. `supabase/migrations/0009_doctor_group_export.sql` — تصدير كشف واجبات المجموعة الكامل للدكتور (`1/0`).
   10. `supabase/migrations/0010_backup.sql` — جدول ودوال النسخ الاحتياطي الأسبوعي والاسترجاع.
   11. `supabase/migrations/0011_cancel_attendance_session.sql` — دالة إلغاء جلسة الحضور المفتوحة بالخطأ.
   12. `supabase/migrations/0012_home_announcements.sql` — إظهار الإعلانات اليدوية في «يهمّني الآن» لمدة 24 ساعة.
   13. `supabase/migrations/0013_label_lecture_en.sql` — دعم وسم `#Lecture_N` بجانب `#المحاضرة_N`.
   14. `supabase/migrations/0014_assignment_allow_text.sql` — دعم خيار السماح بإرسال نصوص/روابط في الواجبات (`allow_text`).
   15. `supabase/migrations/0015_doctor_choice_and_sharek_dedupe.sql` — دعم اختيار المدرس عند التعدد في رفع الملفات، ومنع تكرار النص/الملف المتطابق في «شارك».
3. شغّل مخرجات `python3 scripts/setup_cohort.py --stdout` (أو ملف `supabase/seed_groups.sql`) في **SQL Editor** لإنشاء المجموعات النظرية والعملية.
4. **امنح حسابك صلاحية المطوّر الأول** بتنفيذ الاستعلام التالي في **SQL Editor** (استبدل `123456789` بمعرّف حسابك الرقمي في تيليجرام `Telegram ID`):
   ```sql
   insert into role_grants (telegram_id, role, granted_by)
   values (123456789, 'developer', 123456789);
   ```
   بعد هذه الخطوة، يمكنك إدارة كل شيء (منح صلاحيات المندوبين واللجنة، إضافة المواد والدكاترة، واستيراد الطلاب) من داخل «لوحة المطوّر» في التطبيق المصغّر دون العودة إلى SQL.

### الخطوة 3: نشر الواجهة والـ API على Vercel
1. اربط مستودع GitHub بحسابك في **Vercel**.
2. من **Settings ← Environment Variables** في Vercel، أضف المتغيرات التالية:

| المتغير | إلزامي؟ | الوصف والمثال |
| :--- | :--- | :--- |
| `BOT_TOKEN` | نعم | توكن البوت من BotFather (يُستخدم للتحقق التشفيري HMAC-SHA256 من `initData` ولإرسال الملفات والتنبيهات الفورية) |
| `SUPABASE_URL` | نعم | رابط مشروع Supabase (`https://xxxx.supabase.co`) |
| `SUPABASE_SERVICE_KEY` | نعم | مفتاح الخدمة `service_role` من Supabase |
| `BOT_USERNAME` | موصى به | معرف البوت بدون `@` (مثال: `cs26_bot`) لتوليد روابط الانتقال المباشر للبوت |
| `WEB_APP_URL` | موصى به | رابط تطبيقك على Vercel (`https://your-app.vercel.app`) |
| `COHORT_CONFIG_JSON` | للـ Fork | JSON إعدادات الدفعة في سطر واحد (اتركه فارغًا إن كنت تستخدم `cohort.json` الافتراضي) |
| `GEMINI_API_KEYS` | اختياري | مفتاح أو عدة مفاتيح Google Gemini API مفصولة بفاصلة `,` للتبديل التلقائي عند انتهاء الحصة |

3. بعد انتهاء النشر على Vercel، انسخ رابط التطبيق (`https://your-app.vercel.app`) وضعه في `WEB_APP_URL`، كما يمكنك ضبطه في `@BotFather` عبر `/setmenubutton` (ويقوم البوت أيضًا بضبط زر القائمة تلقائيًا عند إقلاعه إذا وُجد `WEB_APP_URL`).

### الخطوة 4: تشغيل البوت على خادم البوت (Orihost / VPS)
```bash
pip install -r requirements-bot.txt
cp .env.example .env
# حرّر ملف .env وضع نفس القيم (BOT_TOKEN, SUPABASE_URL, SUPABASE_SERVICE_KEY, WEB_APP_URL, ...)
export $(grep -v '^#' .env | xargs)
python3 -m bot.main
```
- يحفظ البوت جلسات المستخدمين الجارية في ملف `bot_state.pickle` (يمكن تغيير مساره عبر المتغير `BOT_STATE_FILE`).
- لتحديث البوت لاحقًا بعد سحب تحديثات المستودع، شغّل:
  ```bash
  ./scripts/update_bot.sh
  ```

## 5. إعداد الكتالوج الأكاديمي وربط الدكاترة والمجتمعات والـ Topics

تعتمد المنظومة على جدول `tg_destinations` لتوجيه كل نوع من المنشورات والتسليمات إلى المجتمع والـ Topic المخصص له في تيليجرام.

### أولاً: إضافة المواد والدكاترة وربط التدريس (من لوحة المطوّر)
افتح التطبيق المصغّر بحساب المطوّر وانتقل إلى **لوحة المطوّر ← المواد والمجتمعات**:
1. **إضافة مادة (`1) إضافة / تحديث مادة`)**: أدخل اسم المادة بالعربية (مثل `شبكات الحاسوب`) والوسم بدون `#` (مثل `شبكات_الحاسوب`).
2. **إضافة دكتور أو معيد (`2) إضافة / تحديث دكتور أو معيد`)**:
   - أدخل اسم الدكتور أو المعيد كما تريد ظهوره في الوسوم والتقارير (مثل `د. أحمد المنصوري` أو `أ. طارق السامعي`).
   - **ربط حساب الدكتور (`Telegram ID`)**: إذا أدخلت الـ `Telegram ID` الخاص بالدكتور، فبمجرد فتحه للتطبيق المصغّر سيتعرف النظام عليه تلقائيًا (`kind = 'doctor'`) ويعرض له **شاشة الدكتور** الخاصة بواجبات مجموعاته وتصدير كشوف الـ Excel، كما يسمح له بالضغط على زر **«✔️ تم الاستلام»** تحت تسليمات الطلاب في مجتمعه.
3. **ربط التدريس (`3) ربط مادة بدكتور ومجموعات`)**:
   - اختر المادة ← اختر الدكتور أو المعيد ← اختر القسم (`نظري` أو `عملي`) ← حدّد المجموعات التي يدرّسها (يمكنك تحديد مجموعة واحدة، أو عدة مجموعات، أو الضغط على `الكل ✅`) ثم اضغط **«حفظ ربط الدكتور بالمجموعات المحددة»**.
   - **كيف يتصرف النظام عند وجود أكثر من دكتور أو معيد لنفس المادة والقسم؟**:
     - في **الواجبات والتقارير**: يختار النظام تلقائيًا المدرس المسندة إليه تلك المجموعة المحددة (`CS2_G1` أو `G2` مثلًا).
     - في **رفع الملفات الدراسية**: إذا كان للمادة والقسم المختارين مدرس واحد فقط، يُختار تلقائيًا دون سؤال الرافع؛ أما إذا وُجد أكثر من مدرس أو معيد لنفس المادة والقسم (مثل معيدَين للعملي)، فيُظهر التطبيق تلقائيًا شريحة **«مُدرس المقرر»** ليختار الرافع اسم المدرس صاحب الملف بدقة.

### ثانياً: ربط المجتمعات والأقسام (`Topics`) بالأمر السريع `/where`
بدلاً من البحث عن أرقام `chat_id` و`topic_id` يدويًا:
1. تأكد أن البوت مشرف (`Admin`) في المجموعة (Supergroup مُفعَّل فيها نظام المواضيع `Topics`).
2. ادخل إلى الـ **Topic (القسم)** الذي تريد ربطه، واكتب الأمر:
   ```text
   /where
   ```
3. سيرد البوت داخل نفس الـ Topic برسالة تعرض `chat_id` و`topic_id` وتحتها **4 أزرار تفاعلية مباشرة**:
   - **📚 ربط بملفات ومحاضرات مادة**: يعرض قائمة المواد، وبمجرد ضغط المادة يربط هذا الـ Topic بمفتاح `cohort:subject:<id>`.
   - **📣 ربط بإعلانات وواجبات مجموعة**: يعرض المجموعات النظرية، ويربط الـ Topic بمفتاح `cohort:notices:<group>`.
   - **📌 ربط بتقارير مجموعة**: يعرض المجموعات النظرية، ويربط الـ Topic بمفتاح `cohort:theory:<group>`.
   - **👨‍🏫 ربط بتسليمات دكتور**: يعرض قائمة الدكاترة والمعيدين، ثم يعرض أزرار المجموعات النظرية (`نظري CS2_G1...`) والمجموعات العملية (`عملي G1...`) لربط الـ Topic بمفتاح `doctor:<doctor_id>:<part>:<group>`.

*(كما يمكنك ربط أو حذف أي وجهة يدويًا من **لوحة المطوّر ← المواد والمجتمعات ← البند 4**).*

### ثالثاً: جدول مفاتيح الوجهات (`tg_destinations`) ومسارات الإرسال

| مفتاح الوجهة (`key`) | مثال للمفتاح | متى يُرسل البوت إليها وماذا ينشر؟ |
| :--- | :--- | :--- |
| `cohort:subject:<id>` | `cohort:subject:1` | عند **رفع ملف دراسي**: ينسخ البوت الملف (`copyMessage`) إلى هذا الـ Topic مرفقًا بـ Caption منسّق يحتوي على وسوم النوع والمادة ورقم المحاضرة/الـ Module واسم المدرس ونوع المحاضرة. وعند استبدال الملف أو حذفه، يحذف البوت الرسالة القديمة من المجتمع تلقائيًا |

## 6. التفاصيل التقنية لآلية الإرسال، الموثوقية، والمجدول الآلي (`Worker`)

يعمل داخل عملية البوت (`bot/worker.py`) محركان متوازيان يضمنان عدم ضياع أي رسالة أو تسليم حتى عند انقطاع الشبكة أو إعادة تشغيل البوت أو تجاوز حدود تيليجرام (`FloodWait`):

### 1) محرك تسليم الواجبات للدكاترة (`deliver_tracked` & `pending_deliveries`)
- **التسليم الفوري + الطابور الاحتياطي**: فور ضغط الطالب على «✅ إنهاء التسليم»، يحجز البوت التسليم لمدة `90` ثانية عبر دالة `claim_delivery` ويرسله فورًا لمجتمع الدكتور.
- **ماذا يحدث إذا لم يكن مجتمع الدكتور مربوطًا بعد أو فشل الإرسال؟**:
  - يُحفظ تسليم الطالب بأمان في القاعدة بحالة `delivery_state = 'pending'` وتظهر للطالب رسالة مطمئنة: *«تم تسليم واجبك ✅ سيصل للدكتور تلقائيًا بمجرد جاهزية المجتمع»*.
  - يعيد المجدول المحاولة بتراجع تصاعدي (`Exponential Backoff`: يبدأ من `30` ثانية ويتضاعف حتى `30` دقيقة كحد أقصى) بحيث لا يحجب تسليمٌ فاشلٌ بقية التسليمات.
  - **إعادة الإرسال الفوري عند الربط (`trg_destination_linked`)**: بمجرد أن يقوم المطوّر بربط Topic الدكتور عبر `/where`، يقوم محفّز SQL (`Trigger`) بتصفير مؤقت الانتظار (`next_delivery_at = now()`) فتصل جميع التسليمات المعلّقة إلى مجتمع الدكتور خلال ثوانٍ!
- **تعديل التسليم وحذف القديم تلقائيًا**: عندما يعدّل الطالب تسليمه قبل إغلاق الواجب، يرفع النظام رقم المراجعة (`revision + 1`)، وعند إرسال النسخة الجديدة لمجتمع الدكتور يقوم البوت أولاً بحذف رسائل التسليم القديم من مجتمع الدكتور (`old_deliveries`) ثم ينشر الملفات الجديدة مع شارة `(تسليم معدَّل)`.
- **إنهاء الرفع غير المكتمل تلقائيًا (`stale_unfinalized`)**: إذا رفع الطالب ملفات واجب للمرة الأولى ونسي الضغط على زر «✅ إنهاء التسليم» لمدة `10` دقائق من آخر ملف، يقوم المجدول بإنهاء التسليم واعتماده وإرساله للدكتور تلقائيًا حتى لا تضيع درجة الطالب؛ أما إذا كان الطالب في وضع «تعديل تسليم سابق» فيرسل له البوت تذكيرًا واحدًا فقط دون استبدال تسليمه القديم بنصف ملفات.

### 2) محرك طابور الإشعارات (`_outbox_loop`)
- جميع الإشعارات الجماعية (واجب جديد، تذكير بواجب، فتح تظلمات، حملة شارك جديدة، إعلان يدوي، نشر تقرير) تُدرج في جدول `outbox` مع مفتاح منع تكرار `dedupe_key`.
- يسحب العامل `25` رسالة في كل دفعة عبر `claim_outbox` (مع حجز `2` دقيقة)، ويرسلها عبر دلو سرعة `TokenBucket(rate=25, burst=25)` لتفادي حظر تيليجرام.
- إذا أوقف طالبٌ البوت (`Forbidden: bot was blocked by the user`)، يعلّم النظام حسابه في `bot_blocked_at` فلا يكرر محاولة الإرسال إليه حتى يعيد الطالب تشغيل البوت بـ `/start`.

### 3) المهام المجدولة دوريًا (`_scheduler_loop` — كل 60 ثانية بتوقيت صنعاء `UTC+3`)
1. **إغلاق الواجبات المنتهية**: يغلق الواجبات التي تجاوزت موعد التسليم المعلن مضافًا إليه **المهلة الداخلية المخفية (`12` ساعة افتراضيًا في `app_settings`)**، بحيث يُسجَّل من يسلّم بعد الموعد المعلن وخلال الـ 12 ساعة كـ «متأخر (`is_late = true`)» قبل الإغلاق النهائي.
2. **إغلاق دورات التظلمات المنتهية**: فور حلول `closes_at`، تُغلق الدورة ويرسل البوت الكشف المجمّع النهائي تلقائيًا إلى مندوب المجموعة.
3. **تذكيرات الواجبات (`24` ساعة، `3` ساعات، `1` ساعة)**: تُرسل للطلاب الذين لم يسلّموا الواجب بعد (حسب تفضيلات كل طالب في الإعدادات).
4. **التذكير المسائي بالتقرير اليومي**: يُرسل الساعة `8:00 مساءً` (أيام السبت إلى الخميس) لأعضاء اللجنة العلمية للمجموعة التي لم يُكتب تقريرها اليومي بعد.
5. **التجميع والنشر الآلي للتقرير الأسبوعي**: مساء كل **خميس الساعة `9:00 مساءً`** بتوقيت صنعاء، يجمّع النظام التقارير اليومية المكتوبة خلال الأسبوع (السبت–الخميس) لكل مجموعة نظرية في رسالة حصاد أسبوعي واحدة بعنوان `📚 الأسبوع N` وينشرها في Topic تقارير المجموعة.
6. **النسخة الاحتياطية الأسبوعية الآلية (`/backup`)**: فجر كل **جمعة بعد الساعة `3:00 صباحًا`**، يصدّر البوت جميع جداول القاعدة بصيغة JSON داخل أرشيف `ZIP` مقسّم (بما لا يتجاوز `40MB` للجزء) ويرسله إلى المحادثة الخاصة لكل مطوّر، مع إمكانية طلب نسخة فورية في أي وقت بإرسال الأمر `/backup` للبوت.

## 7. استيراد الطلاب، استرجاع النسخ الاحتياطية، والاختبارات

### استيراد قائمة الطلاب من ملف Excel
يمكنك رفع ملف Excel مباشرة من داخل التطبيق (**لوحة المطوّر ← الطلاب ← استيراد ملف Excel الآن**)، أو عبر سطر الأوامر باستخدام القالب المرفق `scripts/students_template.xlsx` (الأعمدة: `الرقم الأكاديمي | اسم الطالب | المجموعة النظرية | المجموعة العملية`):
```bash
# معاينة وفحص الملف دون كتابة في القاعدة
python3 scripts/import_students.py scripts/students_template.xlsx --actor 123456789 --dry-run

# التنفيذ الفعلي للاستيراد
python3 scripts/import_students.py students.xlsx --actor 123456789
```

### استرجاع نسخة احتياطية على قاعدة جديدة
بعد تشغيل ملفات الترحيل `0001..0015` على قاعدة Supabase جديدة، شغّل:
```bash
# فحص النسخة الاحتياطية وعرض عدد الصفوف دون كتابة
python3 scripts/restore_backup.py --dry-run backup_2026-11-13_part1of1.zip

# استرجاع البيانات فعليًا
SUPABASE_URL=... SUPABASE_SERVICE_KEY=... python3 scripts/restore_backup.py backup_2026-11-13_part1of1.zip
```
